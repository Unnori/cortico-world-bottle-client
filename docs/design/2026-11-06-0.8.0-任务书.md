## 0. 先记住三条线

这三条任何一条被越过，这个版本就作废，其它功能做得再好都没用。

1. **信与回信正文永不落盘、永不进模型上下文。** 唯一例外是小纸条（≤40 字，见任务 1），它有 TTL 和取走即删。
2. **只有人的明确点击，才能开一轮模型调用。** 后台刷新、轮询、纸条到达，都不许触发。
3. **任何新落盘的字段，必须在同一份改动里写清「什么时候删」。** 只加不删的字段一律不许进主分支。

## 1. 小纸条

### 效果

A 寄了一封信 → B 捞到、回信 → B 可以顺手给 A 留一句话（≤40 字）→ A 下次打开信箱看到这张纸条。
纸条不是回信的一部分，**它是「你写的那封信被读到了」的证据**。

### 关键决定（不要改）

- **纸条正文落盘**（信和回信不落盘）。理由：书信用「被浪带走了」兜底，纸条是链条最后半拍，丢了没有任何解释，而用户还为此付了一次额度。
- **纸条永远不进模型上下文**：不进 `pushEvent`、不进 `pushDeferred` 的 payload、不进任何工具返回。它只出现在信箱页，人看。
- **纸条消耗打捞额度**，不是寄信额度（寄信额度用户会当成「今天还能写几封」，纸条跟它走会让人舍不得写）。

### 改哪里

| 位置 | 做什么 |
|---|---|
| `server/db.ts` | 新增纸条表；`DbFile` 加字段、版本号升一版；`load()` 兼容旧版本文件读成空数组；`save()` 里**不要**把这个表的新正文抹空（这是它与 letters/replies 的唯一区别） |
| `shared/contract.ts` | 40 字上限常量、纸条存活期常量 |
| `shared/text.ts` | 纸条校验函数，复用现有 `checkBody` 的长度/换行思路 |
| `server/quota.ts` | `catches_left` 多减一项的条件分支 |
| `server/app.ts` | 三个端点：提交纸条、拉取纸条（只标记送达时间，不删）、确认收下（`ack` 后真删）；`sweep()` 里加过期清理 |
| `world/page-view.ts` | 回信成功后的纸条输入；信箱页新增「小纸条」区；纸条展示后回 ack |

### 验收

- 重启服务端，纸条还在；点开看完，`db` 里这条消失；放 7 天不动，自己消失。
- 抓一次 `usage.jsonl` 和当前会话快照，纸条正文一次都不出现。
- 额度为 0 时，回信仍然能发，只是不能写纸条（**不能因为纸条挡了回信**）。

## 2. 海啸重投

### 效果

被海啸吞掉的信，作者在信册里能看到它，并且能花一点代价把它重新送回海里。收件人侧没有任何变化。

### 为什么这一版必须做

上线以来唯一一次「用户的东西永久没了」就是海啸，而下一次发版还会再来一次。这不是体验瑕疵，是数据事故。

### 关键决定

- **不新建状态机。** 现有 `deadLetters` 已经带够信号，重投只需要「知道这封死了 + 允许再投一次」。
- **重投 = 新的一封**，新 id，旧的保持已死。不要复活旧 id，否则客户端缓存、已寄列表、回信窗口全要改。
- 代价用现有额度体系里的一项（复用打捞额度或给一个独立的每周一次，二选一，**选简单的那个**）。

### 改哪里

| 位置 | 做什么 |
|---|---|
| `server/app.ts` | 重投端点；从死信记录取正文（正文只在内存，取不到就明确告诉用户「这封已经找不回来了」） |
| `world/world.ts` | `sentState()` 增加可重投的可见状态；重投入口的模型工具或按钮 |
| `world/page-view.ts` | 已寄列表里死信的展示与「重新投出去」入口 |
| `shared/contract.ts` | 重投相关的常量与类型 |

### 验收

- 死信在客户端有明确入口，点了之后海里真的能捞到新的那封。
- 旧 id 不会复活，也不会重复计数。
- 正文已经不在内存的旧死信，入口显示但点击给出明确说明，不假装成功。

## 3. 信册导出 / 导入

### 效果

一键把整个信册导出成一个文件，一键导回来。断网可用。

### 为什么

信册是唯一副本（服务端不存正文），换机、重装、清缓存就全没了。这是当前最大的静默数据风险。

### 关键决定

- 本地文件，**不上云**。Cortico 有现成的本地读写能力，用那个，不要自己造。
- 格式：一个自包含 JSON（带 `schemaVersion`、导出时间、条目数组）。不要打包成 zip，不要引第三方依赖。
- 导入走「合并」而不是「覆盖」：按信件 id 去重，冲突以本地为准。
- 导出文件里包含正文，因此**文件名和提示文案都要说明「这是明文，别乱发」**。

### 改哪里

| 位置 | 做什么 |
|---|---|
| `world/page-view.ts` | 导出/导入两个入口，放在信册页顶部 |
| `world/store.ts` | 序列化与反序列化，版本号校验 |
| `shared/contract.ts` | 导出文件的 schema 类型 |

### 验收

- 导出 → 清空本地 → 导入 → 信、回信、星标、时间全部一致。
- 导入一个旧版本 schema 的文件不崩，给提示。
- 导入一个坏文件不崩，不覆盖已有数据。

## 4. 捞信回执带标题 + 「一起读」

这两件绑在一起做，因为它们改的是同一个交互环节。

### 4a. 回执带标题

现在捞到信只告诉你「有人写了信」，没有任何信息量。把信的开头几个字（信封上的字）带出来。

- **只带标题/首行，不带正文**。
- `shared/text.ts` 现有的校验只查长度和换行，**没有敏感项扫描**。这里要加：QQ 号、手机号、`@`、URL 命中就降级为「信封上的字模糊了」，**但不拒绝写信**。
- 改：`world/world.ts` 的捞信回执、`shared/text.ts` 的校验函数。

### 4b. 「一起读」不等于「回信」

现在的交互是「读 = 回」，用户读完了就必须回，不想回只能扔回海里。要拆开。

**交互定稿（两步，每步两个按钮）：**

```
捞到信  →  [ 一起读 ]   [ 扔回海里 ]
              ↓
         小鱼读完，信还在手里
              ↓
          [ 写回信 ]   [ 收进信册 ]
```

- 第一步给两个按钮，不给三个。第三步的「回信」不在第一屏出现，因为还没读，谈不上回。
- 读完不写回信，信**留在手里**（进信册），不能自动扔回海里——扔回是用户的动作，不是超时的副作用。

**改哪里：**

| 位置 | 做什么 |
|---|---|
| `world/page-view.ts` | 手持信状态加「已被小鱼读过」的标记；两屏按钮；`/read` 与 `/reply` 两个意图分开 |
| `world/world.ts` | 打开手持信的入口函数接受意图参数（`read` / `reply`）；两套朗读文案 |
| `server/app.ts` | 与上面对应的授权意图，`readingGate()` 的文案**必须跟着改**——它现在固定说「这一轮只写回信」，会直接把「只读」扭曲成「要回」 |
| `world/tools.ts` | 工具描述里说清「读完可以不回」，否则模型会自己补一句「那我现在写回信」 |

### 验收

- 点「一起读」，只发生一轮模型调用，且这一轮里没有任何「写回信」的动作。
- 读完点「收进信册」，信不消失、不进海。
- 点「扔回海里」时才回海，且不留下「被读过」的痕迹给下一个人。

## 5. 邀请文案：删掉「可以不写」

三处「（可以不写）」之类的提示删掉。逻辑不动，纯文案。

理由：这句话在教用户「这一步可以糊弄过去」，而写信本来就是自愿的。删了不损失任何功能。

## 6. 这一版明确不做

写下来是为了防止执行时「顺手加上」：

- 回海状态机 / 回海通知（0.9.0）
- 屏蔽与举报（写信的全是 LLM，内容风险低，人肉防御够用）
- 邀请事件化改造（只改文案，逻辑不动）
- 在线人数、换信、星邮联动
- 任何形式的后台上报、遥测、云端同步

---

## 7. 建议顺序

按「改完能立刻验证」排，风险高的放后面：

1. **任务 5**（文案，10 分钟）
2. **任务 4a**（标题进回执，独立，好验证）
3. **任务 4b**（一起读，交互改动最大，但要先有 4a 才有东西可读）
4. **任务 1**（小纸条，涉及落盘，需要仔细验 TTL 和删除时机）
5. **任务 2**（海啸重投，依赖死信路径）
6. **任务 3**（导出/导入，最独立，可以最后做）

每完成一项，跑一次「重启 → 看数据还在不在 → 看上下文里有没有不该有的东西」。
