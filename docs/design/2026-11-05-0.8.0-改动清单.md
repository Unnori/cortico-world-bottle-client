# 漂流瓶 0.8.0 改动清单（交接给执行 Agent）

基线：0.7.4（2026-11-05）
目标：把「被捞起 → 没人回 → 回海」讲完整；把海啸造成的损失变成可挽回；让信册可以带走；给「小纸条」一个不贬值的价格。

四条不能破的底线（每一处改动都要对照）：

1. 正文不落服务端磁盘；服务端只留「谁寄过、谁捞过、投递过几次」。
2. 模型不能寄信。寄出只发生在人点的那一下。
3. 不碰别的 World，不写人格记忆，不把信的内容塞进 `PARTNER.md`。
4. 新增协议字段一律 optional；老客户端连新服务端、新客户端连老服务端都不能崩。

## 0. 先对齐三个事实

### 0.1 回信窗口：代码默认仍是 72，线上是 24

当前源码里有两个 72：

- `shared/contract.ts:250`：`export const REPLY_WINDOW_HOURS = 72;`
- `server/tuning.ts:155`：`replyWindowHours: 72,`

线上通过 `tuning.json` 或 `BOTTLE_REPLY_WINDOW_HOURS` 热载成了 24，客户端拿 `reply_window_hours` 显示。0.8.0 要把默认值统一改成 24，并把所有写死「72 小时」的注释、文案、测试改成 24 或改成读配置。

必须改的位置：

- `shared/contract.ts:250` → `24`
- `server/tuning.ts:155` → `24`
- `server/app.ts:272`、`server/app.ts:302` 的注释（「72 小时」→「回信窗口」）
- `world/store.ts:31` 的注释（「服务端给的 72 小时窗口终点」→「服务端给的回信窗口终点」）
- `README.md`、`CHANGELOG.md` 里所有 72 小时的说法

不要在客户端写死 24：一律用服务端返回的 `reply_window_hours` / `windowUntil`；只有缺失时才用常量兜底。

### 0.2 0.8.0 上线 = 一次海啸

服务端重启会把所有 `floating` 的信归档为 `tsunami`，正文丢失。这是既有设计，不是 bug。0.8.0 必须把「重投」一起发，否则这次重启会白白伤一批正在等回音的人。

上线顺序见第 8 节。

- `package.json` → `0.8.0`
- `CHANGELOG.md` 顶部加 `## 0.8.0`
- 不新增 `describe.json` 版本字段（当前没有）

## 2. P0-A：让「被捞起又回海」成为一件说得清的事

### 现状（代码事实）

- `server/app.ts:273` 的 `toSea()` 只做三件事：`state='floating'`、清空 `catcherHash/caughtAt/replyWindowUntil`、清 `archivedReason`。它不记「这封信回来过」。
- `sweep()`（`server/app.ts:302`）在 `replyWindowUntil <= now` 时调 `toSea()`，所以 24 小时一到，信悄悄回海。
- `/quota` 只返回 `heldByOthers: string[]`（`server/app.ts:753-784`），客户端只能知道「此刻在不在别人手上」。
- `world/world.ts:1791` 的 `sentState()`：有回信 → `replied`；死亡 → `sunk/tsunami`；在别人手上 → `picked`；否则 `drifting`。
- `world/world.ts:775` 只在第一次捡起时推事件（`pickedNoticed` 布尔），第二次、回海都不推。

用户看到的是：`被人捡起来了` → 24 小时后 → `还在漂` → 又被捡起 → 又回海，全程没有一句解释。这是整个产品情绪落差最大的一处。

### A1 服务端：给信记一条回海履历

`server/app.ts` 的 `toSea()` 改成带原因：

```ts
function toSea(letter: LetterRow, reason: 'timeout' | 'dismissed' | 'abandoned', at: number): void {
  // ...原有的 empty 处理不变，但 empty 分支也要记 returnedCount 吗？
  // 不记：正文都没了，回海没有意义，直接 archived。
  letter.state = 'floating';
  letter.catcherHash = null;
  letter.caughtAt = null;
  letter.replyWindowUntil = null;
  letter.archivedReason = undefined;
  if (reason !== 'abandoned') {
    letter.returnedCount = (letter.returnedCount ?? 0) + 1;
    letter.lastReturnedAt = at;
    letter.lastReturnReason = reason;
  }
}
```

三个调用点必须分开：

| 调用点 | 传什么 reason | 为什么 |
|---|---|---|
| `sweep()`（`server/app.ts:306`） | `'timeout'` | 24 小时没人回，是产品要让作者知道的事 |
| `handleDismiss()` 正常带 id（`server/app.ts:696`） | `'dismissed'` | 有人读了但选择放回海里，也是「回来过」 |
| `handleDismiss()` 不带 id 的死锁兜底（`server/app.ts:666`） | `'abandoned'` | 网络问题，不是选择，不计数、不通知 |

注意：`sink()` 不动，裂开沉底不是回海。

`server/app.ts` 新增 `handleRepost(req, bot)`：

```ts
function handleRepost(req: ApiRequest, bot: BotRow): ApiResponse {
  const at = now();
  resetDaily(bot, dayIn(timeZone, at));
  if (sweep(at)) db.save();

  const payload = asObject(req.body);
  const letterId = typeof payload?.letterId === 'string' ? payload.letterId.trim() : '';
  const source = letterId ? db.letterById(letterId) : null;
  if (!source || source.authorHash !== bot.clientHash) {
    return fail(404, 'not_found', '没有这一封。');
  }
  if (source.state !== 'archived' || source.archivedReason !== 'tsunami') {
    return fail(409, 'not_lost', '这一封不是被海啸带走的，不用重投。');
  }
  if (source.repostedTo) return fail(409, 'already_reposted', '这一封已经重投过了。');
  if ((bot.repostsToday ?? 0) >= currentTuning().repostDailyCap) {
    return fail(429, 'repost_limit', '今天重投的次数用完了，明天再来。');
  }

  const parsed = checkBody(payload?.body);
  if (!parsed.ok) return fail(400, 'bad_request', bodyProblem(parsed.reason, parsed.chars));
  const heading = payload?.topic === undefined ? null : checkTitle(payload.topic);
  if (heading && !heading.ok) return fail(400, 'bad_request', '标题应为 1—20 字的单行文本。');

  const letter: LetterRow = {
    id: newId('l'),
    authorHash: bot.clientHash,
    body: parsed.body,
    ...(heading ? { topic: heading.title } : {}),
    createdAt: at,
    state: 'floating',
    catcherHash: null,
    caughtAt: null,
    replyWindowUntil: null,
    deliveredCount: 0,
    throws: 0,
  };
  db.letters.push(letter);
  source.repostedTo = letter.id;
  source.repostedAt = at;
  bot.repostsToday = (bot.repostsToday ?? 0) + 1;
  db.save();
  return ok({ ok: true, letterId: letter.id, quota: quotaFor(bot) });
}
```

注意：重投**不收寄信额度**。原因是它修补的是一次事故，不是一次新的表达；收额度会让受害者二次付费。用每日 5 次上限防刷就够了。

`handleThrow` 里构造 `LetterRow` 的字段可以抽一个 `newLetter()` 小函数，两处共用，避免字段漂移。

```ts
private async repostLetter(letterId: string): Promise<PageResult> {
  const mine = this.store.sent.find(item => item.letterId === letterId);
  if (!mine) return { ok: false, message: '本机信册里没有这一封的原文，重投不了。' };
  if (mine.repostedTo) return { ok: false, message: '这一封已经重投过了。' };
  try {
    const res = await this.authed(() => this.client.repost(letterId, mine.body, mine.topic));
    if (!res.ok || !res.letterId) return { ok: false, message: '没能放回海里，稍后再试。' };

      body: mine.body,
      ...(mine.topic ? { topic: mine.topic } : {}),
      at: this.now(),
    });
    this.setQuota(res.quota);
    return { ok: true, message: '又放进海里了。' };
  } catch (error) {
    return { ok: false, message: error instanceof BottleError ? error.message : '没能放回海里，稍后再试。' };
  }
}
```

## 5. P0-D：屏蔽与举报

### 为什么

现在收到不适内容，唯一动作是「扔回海里」。而扔回会加 `throws`，等于让受害者承担后果；扔回五次还会让瓶子裂开。这个因果是反的。

`server/app.ts`：

```ts
function handleBlock(req: ApiRequest, bot: BotRow): ApiResponse {
  const at = now();
  const letterId = ...;
  const letter = db.letterById(letterId);
  if (!letter || letter.authorHash === bot.clientHash) return fail(404, 'not_found', '没有这一封。');
  const blocked = new Set(bot.blockedAuthors ?? []);
  blocked.add(letter.authorHash);
  bot.blockedAuthors = [...blocked].slice(-200);
  // 如果正拿在手上，顺手放回海里；不计数、不通知作者
  if (letter.state === 'caught' && letter.catcherHash === bot.clientHash) {
    toSea(letter, 'abandoned', at);
  }
  db.save();
  return ok({ ok: true, released: ... });
}

function handleReport(req: ApiRequest, bot: BotRow): ApiResponse {
  const letterId = ...;
  const reason = ...; // 枚举
  const letter = db.letterById(letterId);
  if (!letter || letter.authorHash === bot.clientHash) return fail(404, 'not_found', '没有这一封。');
  db.reports.push({ id: newId('rep'), letterId, reporterHash: bot.clientHash, authorHash: letter.authorHash, reason, at: now() });
  // 举报即屏蔽：举报者不该继续收到这个人的信
  const blocked = new Set(bot.blockedAuthors ?? []); blocked.add(letter.authorHash);
  bot.blockedAuthors = [...blocked].slice(-200);
  db.save();
  return ok({ ok: true });
}
```


## 7. P1-F：小纸条（三拍的最后半拍）

### 规则（先定死，再写代码）

1. 只有**你寄出的信收到回信之后**，你才能写一张小纸条。
2. 每封回信只能写一张。
3. 40 字上限；没有标题；便签样式，不是信封，没有火漆。
4. 对方**不能再回**。这是链条的终点，不是聊天。
5. 发送消耗**一次打捞额度**（`catches_left - 1`），不占回信额度。
6. 纸条正文同样不落服务端磁盘；生命周期和回信一样：服务端内存里待到被取走，客户端取走后存本机。

第 5 条是「珍惜」的来源：用户不是在「用一张免费配额」，是在「用一次新的相遇，换一次把旧话说完整」。这个选择本身就会让人犹豫。

```ts
note?: { id: string; body: string; at: string; from: string };
```

构建方式：`store.notes` 按 `letterId` 分组；`direction==='out'` 挂到 sent，`direction==='in'` 挂到 received。一封信最多一张，不需要数组。

- 在「我寄出的信」里，如果 `item.reply` 存在且没有 `item.note`，底部显示：

```text
写张小纸条（40 字，会用掉一次捞信机会）   [让 Coo 写] [自己写]
```

- 「让 Coo 写」→ `POST /note/request {letterId}`，然后等页面刷新出 `noteDraft`。
- 「自己写」→ 直接展开 textarea，人写，不经过模型。
- 草稿卡片显示：`小纸条 · 40 字以内`，底部两个按钮：`寄出`、`算了`。
- 寄出前提示：`这张纸条会用掉今天一次捞信机会。今天还能捞 N 次。` N=0 时按钮禁用，文案：`今天没有可换的捞信次数了，明天再来。`
- 收到的纸条：挂在「我捞到的信」那一封下面，便签样式，只有正文和「来自 X」，**没有回复按钮**。
- 纸条不显示「已读」次数，不参与星标，不进「一起读信」。

### F5 边界

- 纸条不是信：不进海面池，不会被别人捞到，不占寄信额度。
- 纸条不能举报（没有独立举报入口；如果内容不适，举报原信）。
- 纸条不触发任何唤醒邀请。
- 纸条正文不进 `bottle_mailbox` 的回执，只说「有 N 张纸条」。

### F6 测试

新增 `tests/note.test.ts`：

1. 没收到回信时 `/note` 返回 409。
2. 一封回信只能写一张，第二张 409。
3. 40 字上限，41 字 400。
4. `catches_left` 为 0 时 429，且不扣额度。
5. 成功后 `catches_left - 1`，`bottles_left` 不变。
6. `GET /notes` 只返回发给我的；取走后 `readAt` 有值，`notesUnread` 归零。
7. `bottle_note` 在没有授权时被拒；授权轮里能写。
8. 纸条不能出现在 `/catch` 的池子里。

## 8. 上线顺序（必须按这个顺序）

0.8.0 的服务端重启会造成一次海啸。把伤害降到最低：

1. **先发服务端**（含 `/repost`、`/block`、`/report`、`/note`、`myLetters`），客户端仍是 0.7.4 也能跑（新字段 optional）。
2. 服务端起来后，先确认 `/health`、`/quota` 正常，`myLetters` 对老客户端无影响。
3. **再发客户端 0.8.0**。用户更新后，信册里被海啸带走的信会出现「重新放进海里」。
4. 发一条公告（`tuning.announcement`）：`0.8.0 上线时海面起了一次浪。被浪带走的那封，如果本机还留着原文，可以在信册里重新放进海里。`
5. 观察 48 小时：
   - `repost` 调用数 / 海啸损失数——低于 30% 说明提示不够明显，要改文案；
   - `returned` 状态出现后，7 日内有多少人再次寄信——这是「回海叙事」有没有把人推走的唯一指标。

如果不想这次重启伤到人：提前 24 小时打开 `tideOut.blockThrow`（退潮），让海面自然清空，再发版。代价是 24 小时不能寄信；收益是零海啸。二选一，不要既不停信又指望不丢。

## 9. 不要做的事（0.8.0 明确不做）

- 不做实时聊天、好友、群、广场。
- 不做手机端、组网、LAN 公网化。
- 不做「第四拍」：纸条之后不能再回。
- 不做服务端正文持久化；重投的正文由客户端在用户点击时上传，服务端仍然只在内存里持有。
- 不做举报自动封号；举报只影响举报者自己的海。
- 不做「解除屏蔽」设置页；0.8.0 只增不减。
- 不改 `bottle_write` / `bottle_catch` 的现有语义，不新增第三个写信工具。
- 不把信件内容写进 `PARTNER.md` 或任何人格记忆文件。
